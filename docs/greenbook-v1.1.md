## 01 项目宪章：本次究竟要证明什么

### 1.1 不改变产品身份，改变验证顺序

原报告的产品目标继续保留：西游神话背景、移动端优先、1–4 人合作生存肉鸽、约 15 分钟一局，以及“前期分散冒险，后期共同渡劫”。本次不把产品改成纯单人竞技场，也不删除地形与协作。改变的是：这些系统必须建立在已经成立的基础战斗之上，而不能被用来掩盖基础战斗的问题。[S1，pp.1、63–65]

前期唯一的第一性问题是：玩家只移动，不按攻击键，没有升级、法宝、剧情和美术包装，是否仍然愿意主动接近敌人、判断距离、寻找攻击角度，并再玩一局？

“代码跑起来”与“战斗成立”分别验收。前者由测试与构建证明，后者由实际游玩证明。Codex 可以提交可玩版本、日志与修复，不得自行宣布“已经很爽”。

### 1.2 五层核心结构

| 层级 | 玩家问题 | 本阶段要保护的东西 |
| --- | --- | --- |
| 战斗手感 | 我怎么打？ | 移动响应、攻击空间、命中与敌人反应。 |
| 角色差异 | 我与别人有什么不同？ | 最舒服的站位、攻击角度与换位节奏。 |
| 本命 + 法宝 + 修行 | 这一局怎样成长？ | 本命保持身份；法宝改变搭配；修行有限调节。 |
| 地图与劫难 | 我在哪里打？ | 地形改变路线和选择，不只是背景。 |
| 多人合作 | 我们怎样一起渡劫？ | 分散、支援、集合、守点和救人。 |

### 1.3 五条不可被临时需求推翻的规则

第一，未通过单角色手感验收，不扩充角色与内容。第二，普通攻击的实现可以先于成长系统，但它在产品设计上仍是本命法门的基础层，不新增第四条成长线。第三，所有基础攻击自动执行，玩家负责移动；任何角色都不能依赖队友才有基本输出。第四，表现不能反过来决定伤害，动画和粒子不得成为命中事实来源。第五，新增系统必须说明它验证什么，以及失败后如何撤回。

原稿已经要求辅助能够单人通关、五阶发生形态变化，并警惕角色最终都变成“自动攻击 + 范围越来越大”。本绿皮书把这些要求提前成开发门禁，而不是另起一份不相干的策划。[S1，pp.4、11、23、59]

### 1.4 决策等级

“继承”表示沿用 V1.0；“本次调整”表示接受本次用户提案；“工程建议”表示为执行补足的实现选择；“实验参数”表示可以调，但必须保留修改记录。后文未注明来源的具体数字、技术结构和验收阈值均为本绿皮书提出的工程建议或实验参数，不是原报告已有结论。

### 2.2 不制造重复系统

推荐设计关系如下：

```text
角色
  ├─ 本命法门（唯一的一套角色成长）
  │    ├─ 基础攻击通道：棍扫 / 耙扫 / 经文弹 / 枪芒
  │    └─ 本命衍生通道：如来神掌等，后续开放
  ├─ 法宝：最多两件，后续开放
  ├─ 修行：被动修正，后续开放
  └─ 主动大招：独立操作入口，后续开放
```

程序可以用不同组件执行基础攻击和本命衍生效果，但产品层面不能因此出现两套本命等级、两个主武器槽或两份重复升级牌。V0.1 的“没有技能”，具体含义是：只有基础攻击通道；所有衍生、法宝与大招均未实现。

### 2.3 应同步更新的项目材料

V1.1 被采纳后，原报告中的 MVP 章节、四角色设计表、唐僧本命示例、开发排期、技术架构和验收目标应共同更新。保留原 V1.0 作为历史来源，不覆盖删除。仓库中的当前任务必须引用 V1.1 的阶段范围，避免 Codex 从旧报告再次读出“首版要做四人联机”。

## 03 版本路线与不可跨越的门禁

### 3.1 版本号的含义

V1.1 是策划文件版本；V0.1–V0.6 是未来原型里程碑名称。它们不是已经发布的构建。执行包中的所有开发任务初始状态都是未开始。

| 里程碑 | 允许做什么 | 退出条件 |
| --- | --- | --- |
| G0 / 工程基线 | 环境确认、空场景、运行说明、最小测试入口。 | 他人能按 README 打开，版本与依赖可复现。 |
| G1 / 战斗原型 V0.1 | 一个悟空、一个普攻、一类小怪、灰盒场地、死亡重开。 | 三分钟闭环无阻断错误；真人认可移动、空间和反馈值得继续。 |
| G2 / 角色原型 V0.2 | 同一场地加入八戒、唐僧、哪吒的基础攻击。 | 不靠名字和技能，能感知不同站位与换位策略。 |
| G3 / 本命原型 V0.3 | 只加入唐僧五阶掌印样例，调试切阶。 | 成长改变空间策略，普通攻击仍然有价值。 |
| G4 / 构筑原型 V0.4 | 灵蕴、三选一、最多两件实验法宝、少量修行。 | 成长不会抹平四角色；选择有可解释差异。 |
| G5 / 玩法切片 V0.5 | 一种地形机制、简单妖潮、一个可读 Boss，再验证主动大招。 | 从战斗玩具进入有目标的短局，不依赖内容堆砌。 |
| G6 / 合作切片 V0.6 | 先双人，再四人；共享等级、独立构筑、救援与合流。 | 网络结果一致；“分散 → 集合”的体验经实际联机验证。 |

黑风山完整 15 分钟流程、六类敌人和更多法宝，属于通过 G6 后的产品切片扩充，不自动成为 G5 或 G6 的最低工作量。

### 3.2 失败之后做什么

G1 失败：暂停扩内容，只对移动、攻击几何、攻击节奏、敌人压力和命中反馈迭代。不是删除项目，也不是停止修问题。G2 失败：先调整四种攻击空间，不用堆技能弥补。G3 失败：撤回掌印复杂度，先验证一个掌印的落点与预警。G6 失败：区分同步故障与合作动机不足，不能只给怪加血。

连续三个对照迭代仍无明显改善时，开一次方向复盘：问题是假设错误、实现错误，还是测试场景不成立。每次只记录一个主假设，不同时改十个参数。

### 3.3 早处理风险，不早开发完整功能

移动端和多人是原产品的重要约束，不能等到内容完成才第一次讨论。G0 确认目标平台、构建方式和未来权威来源；G1 后尽早做一次目标设备空场景及基础战斗构建。联网仅预留身份、事件和伤害归属边界，完整房间、匹配、复活和同步不得进入 G1。

如未来发行平台的导出链路尚未确认，将它列为技术阻断项；不得把“Unity 能做移动端”直接等同于“特定小游戏平台必然能发布”。

## 04 默认技术方案与开工确认

### 4.1 推荐基线

本绿皮书推荐 Unity 6.3 LTS + C#，使用轻量 3D 场景与正交相机表现 2.5D；逻辑在 XZ 平面运行。先在桌面环境验证输入与战斗，再检查目标移动设备。Unity 官方列出的 6.3 LTS 支持周期到 2027 年 12 月；这不等于要求采用某个未经检查的最新补丁。[S3]

这是一条执行默认线，不是原报告已经选定的引擎。已有可用 Unity、Godot 或 UE 工程时，T00 必须先评估迁移成本；没有负责人批准不得为匹配本文而重建工程，也不维护三套实现。

| 项目 | 默认决策 | 边界 |
| --- | --- | --- |
| 编辑器 | Unity 6.3 LTS 的一个确切补丁。 | 由本机验证后写入 ProjectVersion.txt，不使用浮动版本。 |
| 渲染 | URP 简单材质、正交相机。 | 不做复杂光照、后处理、正式角色美术。 |
| 输入 | Input System，移动输入抽象为 Vector2。 | 包版本用实际兼容安装结果锁定，不混用两套输入后端。 |
| 地面运动 | CharacterController，平地、禁跳跃、无刚体击飞。 | 仅与 WorldSolid 阻挡；不依赖怪物刚体互推。 |
| 战斗判定 | XZ 平面解析几何 + 墙体遮挡查询。 | 不用挥动武器的 MeshCollider 当攻击事实。 |
| 数据 | JSON 参数源 → 编辑器生成配置资产 → 运行时副本。 | 不让 JSON 与手工 Inspector 改值同时成为权威源。 |
| 测试 | Unity EditMode + PlayMode + 人工试玩。 | Python 规格检查不是 Unity 编译或游戏验收。 |
| 协作 | Git、小任务、每个任务一份证据。 | 暂不引入联网 SDK、ECS 或通用技能编辑器。 |

### 4.2 T00 必须确认的事实

记录实际开发系统、Unity 完整版本、目标导出平台、输入设备、是否有已有仓库、参与人员角色、可用于验收的真实设备，以及本地 Codex 是否有项目目录与命令执行权限。未知项标为待确认，不伪造配置、设备或团队人数。

新项目可先按单名程序与一名验收负责人配合来拆分职责，同一个人可以兼任。这个角色划分不是对用户现有团队的事实描述。

### 4.3 不作出的承诺

不承诺几天开发完成，不承诺所有手机稳定 60 帧，不承诺云端 Codex 环境自带 Unity 或可用许可证，不承诺任意小游戏平台可以直接导出。每一项都必须在相应门禁中用真实环境验证。

## 05 V0.1 的范围合同

### 5.1 玩家实际会经历什么

进入一张简陋平地，看到火柴人式悟空。WASD 或方向键移动，附近的小怪缓慢逼近；怪物进入可攻击空间后，悟空自动朝目标起手并挥棍。玩家能看到攻击覆盖区、受击变化和击退。玩家可以死亡，用一次操作重开；也可以完成三分钟观察局后立即再试。

移动、普通攻击、受击、死亡和重开必须一起形成最小闭环。只有角色能挥棍、但没有威胁和失败的演示，不算 V0.1。

### 5.2 必做、可调与禁止事项

| 类别 | 范围 |
| --- | --- |
| 必做 | 一个角色；一种扇形攻击；一种追击小怪；生命与死亡；稳定输入；墙体阻挡检查；重开；必要调试可视化。 |
| 可调 | 攻击半径、角度、前摇、间隔、移速、怪物速度、伤害、击退和简单音效。 |
| 有条件加入 | 最多三块灰盒障碍，仅用于遮挡与碰撞验收；关闭障碍仍能测试基础手感。 |
| 禁止进入 G1 | 其他角色、掌印、法宝、主动技能、经验、三选一、宝箱、商店、剧情、Boss、账号、广告、联机、存档与正式美术。 |

“不做 UI”指不做产品菜单与装修，不是让测试者看不见生命、时间和重开入口。最小生命显示和开发调试面板是验证工具，不算范围膨胀。

### 5.3 初始场景规格

场地 30 × 30 米，地面 Y=0，边界阻挡，中心出生；逻辑单位 1 单位 = 1 米。怪物默认最多 32 个，初始 3 个，此后每 6 秒尝试生成 2 个，达到上限就跳过本次生成，不积压成下一波爆发。

生成点从预设有效位置中选择，距玩家 6–9 米；不能在墙内、玩家身上或失效区域生成。若没有合法点，本次跳过并计数。出现前给出 0.6 秒简单地面提示，不把突然贴脸生成当难度。

三分钟结束是观察节点，不是通关奖励系统。可显示“本轮结束：重开 / 继续练习”，练习模式不进入正式结果统计。所有初始数字均为实验参数。

### 5.4 完成定义

负责人从干净版本启动，不需要逐个手动拖组件；连续玩三分钟，能感知攻击边界、理解受伤原因、完成死亡与重开。控制台无异常；重开后没有上一局子弹、锁定目标、击退或计时器残留。最终通过还需要第 17 章的人类手感门禁。

## 06 空间、碰撞与输入契约

### 6.1 先统一“距离”的意思

所有战斗距离在 XZ 平面计算，忽略武器模型和角色头部高度。角色逻辑位置是地面中心，攻击原点默认等于该位置。扇形半径从攻击原点量到扇形弧线，不能再偷偷加上角色体半径。敌人的受击圆半径另行参与相交测试，因此敌人边缘进入攻击区时即可受击。

悟空、八戒的半径指扇形几何半径；哪吒的长度指枪芒胶囊中心线长度，实际最远边缘还包含半宽；唐僧的射程指弹体从逻辑发射点走过的最大路径长度。四种数值不能在程序里当同一种“距离”随意替换。

### 6.2 碰撞体与视觉分离

玩家移动半径默认 0.35 米，怪物移动与受击半径默认 0.30 米。角色高度只用于地面控制器及表现，建议玩家胶囊高 1.4 米，中心在离地 0.7 米处。根节点保持地面坐标，Visual 子节点承担动作、缩放与受击闪烁。

WorldSolid 阻挡玩家和怪物移动；Actor 与 Actor 之间默认不发生刚体硬碰撞。怪物使用有限软分离避免完全叠成一点，不能把玩家挤飞，也不能靠物理堆叠把角色弹到墙外。攻击判定读取登记的受击圆，不读取武器模型外形。

地面仅为平面，不支持跳跃、斜坡、台阶、跌落和动态地形。墙体为静态盒体；移动与击退都走同一个地面运动入口，不允许伤害脚本直接瞬移 Transform 穿墙。

### 6.3 输入映射

移动输入先限制长度不超过 1，再映射到相机在地面的右向和前向。按住斜方向不能更快。按键释放后不保留明显漂移；加速默认直接响应，后续才比较轻微平滑版本。移动方向与攻击朝向分离，玩家可以后退同时朝前挥棍。

自动攻击不等于自动追敌：系统可以选敌、转向和起手，但不能替玩家走进攻击范围。没有目标时不空挥；需要测试空挥时，仅由调试开关开启，并排除在正式试玩结果之外。

### 6.4 相机和画面尺度

建议相机俯角约 55°、固定方位、正交投影。初始 Orthographic Size 为 10，先用地面标尺验证 8 米弹体射程和 30 米场地的实际可见关系，再按测试窗口调整。相机跟随在表现更新阶段平滑处理，不能影响逻辑瞄准方向。

默认测试窗口 1280 × 720；另测窄屏比例，避免边缘目标长期在画外被自动选中。V0.1 不依赖镜头震动才能辨认命中。

## 07 四角色 Combat Profile：先有空间，再有数值

### 7.1 共通定义

四个角色仅在 G2 全部开放。G1 只使用悟空配置。表中普通攻击参数为第一轮可运行起点，不是平衡结论，也不代表应由 Codex 一次实现四人。

| 角色 | 作战空间 | 初始几何 | 攻击周期 | 单次目标上限 |
| --- | --- | --- | --- | --- |
| 悟空 | 中近距离横向扫群。 | 半径 2.60 米，扇形 110°。 | 0.80 秒 / 40 tick。 | 6。 |
| 八戒 | 更贴身，覆盖侧方。 | 半径 1.90 米，扇形 240°。 | 1.20 秒 / 60 tick。 | 12。 |
| 唐僧 | 远距离保持间隔。 | 弹体路径 8.00 米，半径 0.16 米。 | 0.44 秒 / 22 tick。 | 每弹 1。 |
| 哪吒 | 中远距离对齐敌列。 | 瞬发胶囊线段长 4.60 米，全宽 0.40 米。 | 0.36 秒 / 18 tick。 | 每击 3。 |

八戒“范围大”优先指角度大、对两侧敌人的覆盖大，不等于半径最长。按理想扇形面积计算，悟空约 6.49 平方米，八戒约 7.56 平方米；八戒的覆盖面积略大，但玩家必须更贴近敌人。该比较只描述几何，不是伤害或强度结论。

### 7.2 起手、命中与收势

统一模拟频率 50 Hz，1 tick = 0.02 秒。下表中的周期是两次攻击起手之间的最小间隔。

| 角色 | 前摇 tick | 有效表现 tick | 后摇 tick | 额外等待 tick | 前摇/有效段移动倍率 |
| --- | --- | --- | --- | --- | --- |
| 悟空 | 9 | 3 | 10 | 18 | 0.90。 |
| 八戒 | 18 | 4 | 16 | 22 | 0.65。 |
| 唐僧 | 4 | 1 | 3 | 14 | 1.00。 |
| 哪吒 | 3 | 2 | 4 | 9 | 1.00。 |

四段之和必须等于攻击周期。伤害只在第一个有效 tick 判定一次，剩余有效段是动作与命中可读性窗口，不是每帧重复扣血。后摇和等待段移动倍率默认恢复 1.00。不能在周期之外又叠加一份同样长的冷却。

### 7.3 角色化数值与对照模式

| 角色 | 单次伤害 | 基础移速（米/秒） | 生命 | 对普通怪击退 |
| --- | --- | --- | --- | --- |
| 悟空 | 18 | 5.0 | 100 | 0.35 米，0.10 秒完成。 |
| 八戒 | 28 | 4.2 | 160 | 0.80 米，0.16 秒完成。 |
| 唐僧 | 8 | 4.6 | 90 | 不击退。 |
| 哪吒 | 7 | 5.8 | 90 | 0.08 米，0.08 秒完成。 |

唐僧弹速默认 12 米/秒，不追踪、不弹射、不穿透。哪吒暂不生成飞行弹体，枪芒在命中 tick 一次判定整段空间，避免与唐僧变成同一种弹幕角色。

“八戒换血”不等于可无限站桩。V0.2 不附赠吸血、回血、嘲讽或无敌；先凭更高生命、宽角度与强击退验证贴身打法。若仍不成立，再单独提防御机制实验，不能悄悄加被动救设计。

提供一个“等基础属性对照”开关：四角色统一移速 5.0、生命 100，保留各自攻击形态、时序和攻击移动倍率。先辨认攻击空间差异，再恢复角色化属性。不要用坦度和跑速掩盖攻击设计同质化。

### 7.4 每个角色的成功与失败征兆

悟空成功：玩家会把怪群放在棍端附近，找机会扫多只；失败：必须脸贴怪才能打到，或者只要倒退就永远安全。八戒成功：愿意短暂贴近，接受慢起手换侧向覆盖；失败：只是范围和伤害都更大的悟空，或前摇让移动像失灵。

唐僧成功：会维持距离、利用弹道与障碍，单人仍能处理敌人；失败：只是在更远处自动扣血，没有弹道或被逼近的压力。哪吒成功：主动调整位置把敌人排成线；失败：射线宽到像扇形，或每次自动转向让站位毫无意义。

## 08 自动攻击的完整时序与选敌规则

### 8.1 攻击状态机

```text
Ready → Windup → Active → Recovery → CooldownWait → Ready
              死亡可中断尚未结算的未来攻击
```

起手时创建 AttackId，记录 source、startTick、hitTick、方向、配置版本与目标身份。hitTick = startTick + windupTicks。nextEligibleTick = startTick + periodTicks。动画时长不能反过来修改这两个时刻。

一个角色同时最多一份基础攻击实例。卡顿恢复后不能在同一渲染帧凭累计计时器爆发十次攻击；每个模拟 tick 按状态推进，最多按规定创建下一份实例。若因长卡顿丢弃过量累计时间，必须统计 simulationBehind，而不是假装无损追赶。

### 8.2 选敌范围与稳定性

Ready 状态每 5 tick 最多扫描一次候选；按是否存活、是否敌对、几何上能否触及、是否被墙体完全挡住过滤，再按中心距离与稳定身份排序。候选的触及检查使用“指向该候选的试瞄方向”，而非当前武器朝向，因此身后的敌人也可被选中；只有下一次起手时才能转向，不能在一次横扫中跟着不同敌人连续转圈。

保留仍可攻击的当前目标；新目标只有在距离小于旧目标的 80% 时才替换，防止距离接近的两只怪让武器来回抖动。这个滞回只影响 Ready 状态。目标死亡、离开触及范围或被墙遮挡时立即失效，不等待比例条件。

扫描与攻击判定共享同一套范围语义。对哪吒要考虑胶囊端部，对唐僧要考虑弹体半径，不可因为一处用中心点、一处用外缘而出现“明明能打到却不出手”。

### 8.3 起手之后不临时改题

攻击方向在起手时锁定；攻击原点在命中 tick 取角色当时的地面位置。也就是说玩家仍能移动带动出手位置，但不能靠前摇中的自动转向把扇形变成隐形圆形。目标在前摇中死亡或跑出范围，本次攻击仍按锁定方向完成，可能落空。

扇形和枪芒命中时重新查找实际落在攻击形状中的所有合法敌人；锁定目标只是瞄准依据，不是唯一受击对象。唐僧在 hitTick 发出一个弹体；之后碰到谁由弹体路径决定，不直接给原锁定目标扣血。

### 8.4 单次攻击只命中一次

使用 AttackId + EntityRef 记录已命中对象。EntityRef 至少包含对象池槽位与 spawnGeneration，同一池对象重新出生必须获得新代际；不能只用 GameObject 引用或池槽号表示一生。

同一怪物有多个碰撞子节点，也只能被一次攻击结算一次。目标数上限先做稳定排序再截取：扇形按与原点距离；枪芒按沿线投影距离；并列按 EntityRef。不能让引擎返回数组顺序决定谁受伤。

### 8.5 一个 tick 的结算顺序

建议由单一 CombatWorld 驱动：读取输入快照 → 更新敌人意图 → 移动与击退 → 更新攻击状态 → 收集命中 → 按稳定顺序应用伤害 → 处理死亡 → 发送表现事件 → 回收对象。

同一 tick 内，在命中收集时仍存活的双方允许互相命中，避免脚本执行顺序决定胜负。死亡立即阻止以后 tick 的出手；当前 tick 已收集的有效事件不因表现先后被任意撤回。一次死亡只发送一次事件，循环结束后再修改集合，防止迭代中删除引发漏算。

## 09 命中几何：必须可单元测试的规则

### 9.1 共通输入与误差

所有函数接收二维原点、标准化方向、攻击形状和敌人受击圆。默认边界包含相切，比较容差 epsilon=0.0001 米。输入半径、长度、速度必须为有限非负数；方向长度为零时使用上次有效朝向，仍无有效值则固定世界前向。

宽相只负责找候选，窄相决定命中。调试图形从相同参数和方向生成，不允许判定 110°、特效却只画 80°。圆弧显示可以离散近似，但采样误差不能改变逻辑边界。

### 9.2 扇形与受击圆相交

将敌人中心换算到以攻击方向为前向的局部坐标 q，距离为 d，半角为 a。计算敌人中心到“有界扇形区域”的最短距离，再判断该距离是否小于等于敌人受击半径。

当中心角度落在扇形内，最短距离为 max(0, d - R)。当中心角度落在扇形外，分别计算中心到两条边界线段的距离，取较小者；线段从原点到半径 R 的两个角边端点。最后比较 enemyRadius + epsilon。中心与原点重合时距离为零；360° 特判为圆形。

这个办法同样覆盖八戒 240° 的大扇形。禁止直接用“敌人中心在角度内，且距离 ≤ R + enemyRadius”代替完整相交：那种简化会漏掉角边擦中，并使角落判断与画面不一致。

### 9.3 圆形与胶囊线段

圆形区域命中条件：敌人中心到技能圆心的距离 ≤ 技能半径 + 敌人半径 + epsilon。

胶囊线段命中条件：敌人中心到线段 AB 的最短距离 ≤ 枪芒半宽 + 敌人半径 + epsilon。投影参数 t 必须限制在 [0,1]；退化为零长度时当作圆处理，避免除零。哪吒长度 4.60 米、半宽 0.20 米，几何边缘最远为 4.80 米，不含敌人半径。

### 9.4 弹体必须做连续路径检查

唐僧弹体每个 tick 从旧位置走到新位置，用扫掠圆/球检查整段路径，而不只查新位置是否重叠。先处理出生位置的重叠，再按沿路距离排序所有潜在命中。墙比敌人近时先撞墙；敌人在墙前时先打敌人。默认墙优先处理几何上几乎同距的事件。

弹体逻辑发射点设在角色地面中心对应的攻击高度，视觉可以在前方 0.4 米处显示经文，但逻辑路径不能从墙外开始。最大路径长度严格为 8 米；最后一步截短到剩余距离，不能越过终点再回收。命中一次、撞墙或走满射程即回收，不继续寻找第二个敌人。

若使用 NonAlloc 物理查询，结果顺序不得假设已排序，缓冲区满也不得静默漏掉命中。V0.1/V0.2 可以改用已登记敌人的线性候选检查，墙体查询仍明确处理容量与阻挡顺序。具体引擎 API 签名须在锁定版本中编译验证。

### 9.5 墙体与近战

扇形或枪芒覆盖到敌人后，还要检查攻击原点到该敌人中心的 WorldSolid 遮挡。V0.1 采用中心连线遮挡规则，因此墙角边缘有时会保守拒绝命中；它是明确取舍，不是随意漏判。枪芒视觉在第一堵墙处终止，不能显示穿墙却无伤害。

掌印以后采用从落点到目标的局部遮挡，不采用从唐僧到每个目标的无限穿墙射线。所有攻击默认不穿 WorldSolid，未来需要例外必须成为显式配置与测试。

### 9.6 必测的几何边界

至少覆盖：扇形正前方、正后方、角边相切、弧线相切、超出边界、240° 的侧后方、原点重合、零半径、胶囊侧边与端点、退化线段、弹体高速跨越小目标、出生重叠、墙前敌人、墙后敌人、多个受击体以及对象池身份复用。

执行包内的 Python 几何参考和测试仅用来建立可复用的规格预期；Unity 实现仍必须有对应的 EditMode 测试。两边一致才说明规格被落实，不能把 Python 测试通过写成“游戏验证通过”。

## 10 怪物、伤害、受击与死亡

### 10.1 第一类小怪

唯一基础小怪为“追击妖”。生命 24，移动速度 2.4 米/秒，受击圆半径 0.30 米；以玩家位置为追击目标。状态仅包含 Chase、Windup、Recover、Dead；不做行为树、仇恨系统或远程攻击。

它的近战攻击区域为以自身中心为圆心、半径 0.45 米的圆，玩家受击半径另加 0.35 米，因此双方中心距约 0.80 米时具备接触攻击条件。前摇 12 tick（0.24 秒），在命中时重新检查距离和遮挡；攻击周期 50 tick（1 秒），单次伤害 10。

前摇给出明显但简陋的蓄势提示。玩家离开范围则小怪打空；绝不把每帧碰撞回调都当作一次攻击。攻击朝向与表现固定，第一版圆形接触攻击不承诺可从背后躲避其几何。

### 10.2 追击与分离

先使用直线追击和短距离局部分离，怪物移动方向归一化后乘速度。软分离强度有限，不能比追击更强导致怪群向外爆开。32 个怪物允许简单线性或成对检查；只有实测成为瓶颈才引入网格索引。

在无障碍场地验证追击；在三块障碍场地验证“不穿墙”。V0.1 不承诺复杂寻路，怪物可能被简单障碍阻挡，但不能持续抖动或穿透。需要绕行玩法时，在 G5 单独引入导航与路线规则，不把临时避障冒称完整导航系统。

### 10.3 伤害事务

DamageEvent 至少包含 AttackId、SourceRef、TargetRef、命中 tick、基础伤害、命中位置、击退方向和配置版本。生命逻辑只接受合法事件；伤害数值不从粒子回调读取。生命降到零时触发一次死亡，立即标记为不可选取并取消未来攻击；登记表的结构性删除统一放在 tick 尾，避免遍历中修改集合。

玩家受到一次有效伤害后获得 20 tick（0.40 秒）的全局受伤保护，目的是避免同一怪堆在同一瞬间把测试者清零。保护期间拒绝伤害也要计数，显示明确闪烁，不隐藏规则。怪物没有这种全局保护，仍用每攻击去重。

### 10.4 击退不是额外瞬移

击退被转换为一段受墙体约束的位移，和正常移动在同一入口合成。悟空把普通怪推开 0.35 米，八戒推开 0.80 米；墙挡住时实际位移变短，不穿墙、不把目标传送到墙另一侧。

受击抖动不自动重置怪物攻击冷却，也不默认取消其前摇。攻击失败应主要因为击退让双方距离不再满足命中，避免每一击都形成隐性永久控制。多次击退叠加要限幅，初始限制为任意 0.20 秒内累计请求位移不超过 1.00 米；该限幅针对普通怪，后续精英与 Boss 另设规则。

### 10.5 重开契约

R 键或简单按钮重开。所有敌人、弹体、攻击实例、延迟落点、目标锁定、受伤保护、击退、模拟计数和调试统计必须清零。随机种子按测试场景重置以便对照；runId 更新，旧事件即使迟到也不能打中新一局对象。

## 11 手感不是特效：反馈层级与实验方法

### 11.1 三层反馈

动作层：武器沿明确路径运动，起手、接触和收势可辨，八戒比悟空更有准备时间。对象层：命中目标闪烁、压缩或短促偏移，受到可预测击退；死亡有清楚的退场。感官层：轻量音效和可关闭的小幅镜头反馈。先有前两层，再添加第三层。

默认命中闪烁 0.08 秒、死亡退场不超过 0.25 秒。重击可冻结武器视觉约 0.04 秒，但不修改全局 Time.timeScale，不暂停伤害计时、敌人逻辑或输入。局部视觉冻结只能增强重量，不能成为逻辑控制效果。

### 11.2 明确禁止的“伪爽感”

不靠持续全屏震动、不靠伤害数字遮满屏、不靠把所有敌人速度降到追不上任何角色、不靠把攻击范围放大到看不到边界、不靠自动吸附玩家到目标身边。关闭音效和镜头反馈后，攻击区与受击关系仍应成立。

### 11.3 每轮只回答一个问题

例如“悟空需要比现在远 0.3 米才能产生棍端距离感”。保持怪物、伤害、移速和地图不变，对比 2.3 / 2.6 / 2.9 米三个配置。记录测试者是否靠近、何时受伤、平均一次扫中几只，以及主观描述。不要同时提高伤害、角度和攻速后把改善全归因于距离。

数值不是最后才写：可玩闭环必须有伤害和生命。这里的“数值最后”应落实为“先用占位数值建立几何与节奏，再做平衡精调”，不能用零伤害或无限生命测试完整战斗乐趣。

## 12 调试场景与最小遥测

### 12.1 六个固定场景

| 场景 | 内容 | 主要检查 |
| --- | --- | --- |
| RangeLab | 固定木桩、地面标尺、角边与半径边界。 | 判定与显示一致。 |
| SoloChase | 一个追击怪，无障碍。 | 距离、起手与撤离。 |
| SmallCrowd | 8 个相同怪，从不同方向接近。 | 扫群、锁定抖动、接触压力。 |
| WallLab | 三块矩形障碍，敌人在墙前/墙后。 | 移动、近战遮挡、弹体顺序。 |
| Survival180 | 固定种子的三分钟观察局。 | 可玩闭环与重开。 |
| Stress32 | 32 个怪持续追击，固定录制窗口。 | 分配、帧时间和池回收。 |

V0.1 不需要六张独立地图；一个灰盒场景配六组测试布置即可。每组必须有可复现入口，而不是让负责人手动摆怪。

### 12.2 最小开发面板

F1 显示攻击形状、受击圆和目标；F2 暂停/继续单人模拟；F3 单步；F4 在 G2 后选择角色并重置场景；R 重开。参数变更只能作用于运行时副本，记录本轮 configHash；提交正式改值时回写 JSON 参数源并重新生成配置资产。

屏幕显示当前角色、生命、模拟 tick、攻击状态、锁定目标、活动怪物数和当前配置版本。生命与重开提示常驻；其余可隐藏，避免调试界面干扰真人试玩。

### 12.3 只采对问题有用的数据

每轮本地记录 runId、配置摘要、随机种子、构建提交号、设备信息、角色、存活时间、击杀、攻击次数、有效命中次数、每击目标数、实际受伤次数和空挥率。每秒采样一次最近敌人距离；攻击命中与玩家受伤时再各采样一次。

不只记录“平均攻击距离”：那会混合安全跑图和战斗。区分全局最近敌人距离、实际出手时距离和受伤时距离，才能判断角色是否真的在不同位置作战。性能单独采帧时间分布与相关代码分配；不上传个人信息，不接分析 SDK。

## 13 代码结构：小而可扩展，不先造通用框架

### 13.1 最小责任划分

| 模块 | 负责 | 不负责 |

| InputSource | 读取移动与调试命令。 | 伤害、寻敌、移动角色到目标。 |
| GroundMotor | 地面移动、世界阻挡、击退位移。 | 攻击冷却与伤害。 |
| CombatWorld | 固定顺序推进、实体登记、事件队列。 | 画面粒子、菜单与音效。 |
| AttackController | 选敌、锁向、起手与命中时刻。 | 自行改生命或修改全局时间。 |

| Presentation | 动作、闪烁、声音、死亡表现。 | 判定命中和替代逻辑计时。 |

### 13.3 不可省的两个边界

第一，配置不可变、状态可变。配置资产描述一个角色的默认攻击；运行时状态保存当前 tick、冷却、生命和命中集合。不要把当前生命写回 ScriptableObject 导致下个角色或下次开局继承残值。

第二，实体身份不等于视觉对象。EntityRef 用于战斗事件，GameObject 用于承载表现；对象池复用后身份代际变化。死亡时立即标记不可选取，登记表结构性删除在 tick 尾执行，既避免继续被打，也避免遍历中修改集合。

### 13.4 同步边界只留接缝

保留 ownerId、EntityRef、AttackId、tick 和事件结果字段。单人阶段由 LocalCombatWorld 统一裁定；未来可以由主机或服务器驱动同样的伤害入口。不要提前把所有怪物、子弹与特效做成网络对象，也不要承诺现有物理可以跨设备确定性重放。

## 14 数据合同与配置治理

### 14.1 参数源只保留一份

config/prototype-defaults.json 是可评审的参数源，使用 schemaVersion 和 profileVersion。编辑器导入器负责生成类型化配置资产，场景引用生成资产，构建不读取仓库根目录文件。运行时调参只改副本，不修改共享资产。

每次正式调参提交必须写明：旧值、新值、实验假设、固定条件、测试场景与结论。不得只提交“手感优化”。自动生成文件必须能重新生成；手工制作的场景、材质和角色资产不得被导入器覆盖。

### 14.2 最小攻击配置

```json
{
  "id": "wukong",
  "shape": "sector",
  "rangeMeters": 2.6,
  "angleDegrees": 110,
  "periodTicks": 40,
  "windupTicks": 9,
  "activeTicks": 3,
  "recoveryTicks": 10,
  "waitTicks": 18,

  "moveMultiplierDuringAttack": 0.9,
```

JSON 中角度单位为度，几何函数需要弧度时只转换一次。字段命名标明单位；禁止 range 同时有时表示米、有时表示像素、有时表示直径。派生字段如总周期秒数由 tick 计算，不再手填一份可能冲突的 seconds。

这不是要求先做复杂继承树。V0.1 可以使用简单结构体与明确方法；需求尚未出现时，不建立反射工厂、动态脚本执行、万能效果图或全局服务定位器。

### 14.4 配置校验

导入时检查所有数值有限，周期为正整数，activeTicks 至少为 1，四段之和等于 periodTicks，目标上限大于零，角度在 (0,360]，角色配置的半径/长度为正，移动倍率在 (0,1]，击退距离与时长相容。几何函数另外测试零尺寸退化，不代表当前角色配置允许没有攻击范围。唐僧弹速必须大于零；掌印个数必须与当前阶一致。

遇到非法配置，导入失败并显示具体字段。不要静默夹到“看起来合理”的值，让测试者不知道自己实际测试了什么。运行时若读到不兼容版本，应拒绝启动该测试场景并说明原因。

## 15 场景生成、资产与可复现开局

### 15.1 不让 Codex 靠手写场景 YAML 猜引用

提供一个编辑器入口，例如 Tools/Xiyou/Build Prototype；它使用编辑器 API 创建或更新 Generated 范围内的测试场景、基础材质、预设与配置引用。生成过程必须可重复执行，不重复叠加相机、灯光或角色。

生成器先检查必需脚本和配置已导入；缺项时返回明确错误，不能生成一个勉强打开但引用全空的场景。只有当前任务允许的内容被放入场景：G1 不能因为已有参数表而生成其他三名角色。

### 15.2 生成与手工资产的边界

Generated 目录可以按生成规则重建，但第一次覆盖前检查是否含未提交手工变更；检测到冲突应停止。非 Generated 路径不批量覆盖。新资产由编辑器生成 .meta，已有资产移动时连同 .meta 保留，禁止为“修复引用”统一删除所有 .meta。

README 必须写清：打开哪个项目、哪个场景、是否需要先运行生成器、按什么键、如何重开、如何运行测试。只有脚本没有场景、没有绑定、没有输入配置，不算交付。

### 15.3 最少美术

角色由球体/胶囊/线段组合，武器用棍形或枪形占位；小怪用简单几何体。攻击区域可用半透明网格或轮廓线，不要求购买资产。声音可以使用有明确使用权的占位素材或程序生成短音；每个外部资产记录来源和用途。

正式西游造型、动画、图标、字体与宣传素材进入后续内容阶段。不得从其他商业游戏直接提取资源作为默认工作流。

## 16 对象池、性能预算与测量纪律

### 16.1 从第一版做有限上限，不先做极限优化

V0.1 活动怪物上限 32，预热 32；G2 唐僧弹体上限与预热均为 64；同时显示的伤害数字最多 16，默认关闭。常驻攻击实例按实际角色数复用，临时命中特效按有界池管理。

达到怪物上限时跳过生成；弹体池满时本次发射失败并累计计数，不能偷偷创建无限对象。正常玩法中出现池满本身就是需要调整的性能或设计证据，不应把丢弹掩盖成正常命中结果。

原报告要求怪物对象池、同屏上限，以及最终四人满构筑、Boss 和 150+ 怪物的压力场景。本次保留这些方向，但不会把后期压力场景伪装成 V0.1 已通过的目标。[S1，pp.49–52]

### 16.2 稳态热点

避免在每个 tick 中使用产生临时集合的查询、字符串拼接日志、重复查找全场对象或临时分配命中数组。每个攻击实例复用有界去重集合；视觉和调试日志独立于战斗热路径。

32 个怪先线性扫描，测量后再决定网格。物理与空间索引只保留满足当前需求的最小组合；没有证据，不因为“以后怪很多”就引入 DOTS、复杂 Job 管线或网络对象系统。

### 16.3 建议的初始测量协议

在 T00 登记的真实桌面设备上，以 1280 × 720 独立构建测试，先预热 60 秒，再记录 120 秒。建议观察目标为帧时间 p95 不高于 16.7 毫秒、p99 不高于 33.3 毫秒；这是内部初始预算，不是任意设备的保证。

按独立代码标记检查游戏逻辑稳态每 tick 的托管分配，目标为零；引擎内部、调试窗口和首次预热分配单独记录。记录均值之外，必须记录分位数、最差长帧、内存趋势和池溢出。

### 16.4 移动端不能由电脑代测

G1 后用实际目标设备验证启动、触控映射、相同比例画面和三分钟运行；G2/G4 后再测持续负载与更长时间运行。具体设备型号、系统、分辨率、质量档、温度条件与是否 Development Build 都要写入证据。

原报告的“中端手机”还不是可测试规格。在型号未定之前，状态必须是待验证，而不是“已支持中端手机”。四人后期再加入 64 / 128 / 180 怪分级压测与代表性 Boss/法宝负载，不提前声称达标。

## 17 自动化测试、人工试玩与验收门禁

### 17.1 三类证据不能互相替代

EditMode 证明几何、计时、去重和配置规则。PlayMode 证明场景绑定、移动、伤害、出生、死亡和重开能在引擎中一起工作。人工试玩证明玩家能读懂风险、感知攻击距离，并愿意继续操作。

只有编译通过不能写“验收通过”；只有录像也不能证明没有重复扣血。没有运行的测试写未运行，并附具体阻断原因，不写“预计全部通过”。

### 17.3 G1 人类门禁

先由负责人完成一轮三分钟观察，再邀请 3–5 名未参与编码的人做形成性测试。建议内部通过条件：多数人无需口头解释便理解“接近到棍端、挥击、调整位置”；移动与命中可读性评分中位数至少 4/5；没有两人以上独立报告同一严重控制问题。

这是小样本设计门禁，不是市场统计结论。记录原话、失败时刻和录像位置，不以“大家都说不错”代替观察。测试者人数不足时标记样本不足，不凑造结果。

### 17.4 G2 角色差异门禁

使用同一灰盒角色外观，以 A/B/C/D 代替角色名字，不显示正式技能。先开启等基础属性对照，测试四种基础攻击；随机或轮换体验顺序，再恢复角色化属性复测。

建议邀请 6 人，至少 4 人能够描述其中 3 种以上不同的舒适距离或换位策略，且不是只说“这个伤害高、那个跑得快”。保留同一受试者的出手距离分布与原话。该阈值是内部继续投资的建议，不是科学显著性证明。

### 17.5 不通过时的修复顺序

优先修阻断错误与可读性，再修判定和动作不一致，再调整攻击几何与敌人压力，最后微调数值。不得先加技能、音乐、掉落和奖励遮住问题。每次门禁形成通过、带条件通过或不通过三种结果；条件必须有负责人和复查场景。

## 18 四角色的长期身份护栏

### 18.1 增长可以强化，不应消除短板

悟空的优势是中近距离扇形与控制节奏，不能最终每次都成为全屏圆形。八戒的优势是贴身宽角、重量与承压，不必同时获得最长射程和最高攻速。唐僧的优势是远距输出与周边保护，不应通过不断加宽弹体变成另一位近战。哪吒的优势是窄线、快速和换位，不应每次自动覆盖四周。

这些是基础攻击身份护栏，不禁止觉醒时出现暂时的大范围特效。关键是大招或本命衍生结束后，玩家仍然回到各自的基础战斗空间。

### 18.2 范围修行不能统一放大所有维度

同一个“范围增加”不能同时增加扇形半径、扇形角度、弹体数量、穿透数、掌印个数与法宝范围。建议每种能力显式声明受影响字段：悟空只少量增加半径；八戒优先保持宽角特征；唐僧增加弹体有效距离或小幅弹体尺寸二选一；哪吒控制线宽增长，不能最终成为宽扇面。

进入 G4 前，为每个可成长几何字段设实验上限，并写测试防止修行叠加越界。上限随试玩修订，不先假装已有最终平衡表。

### 18.3 特殊敌人是验证工具，不是早期补救

G1 不做六种敌人。G2 可以用同一小怪的不同速度布置测试距离容错，但不自动升级为新敌人职业。只有四角色在基础怪场景已经清楚不同，才逐步用重甲、远程或控制怪检查其策略边界。

## 19 唐僧“如来神掌”：第一个空间成长样例

### 19.1 归属与开放时机

神掌在 G3 开始，归属于唐僧本命法门的自动衍生通道，不占两件法宝之一，不额外增加主动按钮。经文弹始终保留。关闭本命衍生后，唐僧仍要通过 G2 的单人基础战斗测试。

原报告中的梵音、治疗、护盾与佛光区域不混装进这个原型。它们保留为后续辅助机制或本命变体候选，待空间成长样例成立后再决定。原稿“软职业、可单人”的原则继续有效。[S1，pp.3–4、15–16]

### 19.2 通用施法规则

每 200 tick（4 秒）检查一次施法条件；周围 4.5 米内存在可作用的敌人时启动。没有敌人就保持可施法状态，不向空地图随机砸地；扫描节奏仍为每 5 tick 一次。施法不消耗玩家操作，不打断经文弹。

施法开始记录唐僧地面位置 O 与朝向 theta0。theta0 指向最近可作用的敌人；不可得到有效方向时使用最后朝向。落点围绕 O，圆心轨道半径 2.50 米，每个掌印伤害圆半径 1.05 米；落点一旦预警显示就固定在世界坐标，不跟随唐僧移动。

每掌伤害 12，最多命中 8 个敌人；同一次施法的所有掌印共享命中去重集合，同一个敌人最多承受一次这次施法的伤害。第一个原型不加治疗、眩晕、持续地面伤害和吸附。

### 19.3 五阶定义

| 阶位 | 掌印数量 | 落点与时序 | 主要验证 |
| --- | --- | --- | --- |
| 一阶 | 1 | 面向来敌方向的一个落点，预警 25 tick 后落掌。 | 能否帮助处理逼近路线，而非无目标随机砸地。 |
| 二阶 | 2 | 围绕 O 相隔 180°，同时预警、同时落掌。 | 前后两侧威胁的取舍。 |
| 三阶 | 3 | 相隔 120°，同时落掌。 | 玩家能否围绕三个保护点转移。 |
| 四阶 | 4 | 相隔 90°，按环向顺序在第 25/31/37/43 tick 落下。 | 从纯覆盖进入可读的空间时间节奏。 |
| 五阶 | 5 | 相隔 72°，第 25 tick 同时落下。 | 五点瞬时环阵，清楚区别于四阶逐点落掌。 |

用户描述的五阶文字采用“五个掌印”，本规格严格使用五个，不采用草图中可能被数成六个的符号排列。五阶并不是把圈画满：相邻掌心距离约 2.94 米，两掌伤害圆直径为 2.10 米，中间保留约 0.84 米的几何间隙；不形成无缝永久安全墙。

### 19.4 可直接实现的落点公式

```text
N = rank                 # exactly 1, 2, 3, 4, 5
angle[i] = theta0 + 2*pi*i/N
center[i] = O + 2.50 * direction(angle[i])
impactTick[i] = castTick + 25
if rank == 4:
    impactTick[i] += 6*i
```

预警、落点与伤害共用同一份 center[i]。墙内的落点直接判无效，取消该掌并在调试界面标记；不偷偷重随机到玩家身后。落点有效但局部被墙隔开的目标按遮挡规则不受伤。靠墙时少一掌是可预见空间约束，后续再评估是否需要位置投影，不能在第一版引入未说明的导航搜索。

### 19.5 成长为何不是只加掌印数量

二、三阶扩大可覆盖方向；四阶改变落掌次序，要求理解尚未落下的区域；五阶改变时间结构，形成一次同时保护多个方向的环阵。数量当然增加，但验收重点是玩家是否改变站位、等待和撤离时机，而不是总伤害是否更高。

初始正式本命一阶可定义为“经文弹 + 一个自动掌印”，后续阶位在同一套本命上成长；V0.2 训练底座只是关闭衍生通道的测试模式，不是额外的第零阶装备系统。

### 19.6 G3 专项验收

先完成一掌，再解锁其余阶位。验证落点锁定后唐僧移动不拖走预警、五阶数量恰为五、四阶时序不同、同敌重叠只伤一次、无目标不空放、墙内落点不产生幽灵伤害、重开能取消所有待落掌事件。

给测试者一场“神掌关闭 / 一阶 / 五阶”对照，询问其站位变化。若答案只有“更强了”，而没有“我会等这里落下、再从缺口走”等空间描述，不能仅凭视觉漂亮通过 G3。

## 20 回接本命、法宝、修行与三选一

### 20.1 开放顺序

G4 先接入灵蕴与一条升级流程，再接入有限的三选一；随后只做两件可验证的法宝，而不是照原报告一次做六件。首选候选为芭蕉扇的推开与紫金葫芦的聚拢，因为它们能直接检验“改变敌人位置”与四角色攻击空间的交互。[S1，pp.19–20]

每人最多两件法宝、每件未来可五阶、修行为第三类成长的原约定保留。此阶段不用补齐所有阶位与所有内容；先证明一件法宝不会让基础攻击失去存在感。[S1，pp.19、21–23、64]

### 20.2 三选一不是三个永久装备格

卡牌候选按本命、法宝、修行分类，但不是每次机械地保证各一张。先使用可复现种子的受控候选规则：至少一个合法的已有构筑成长方向；其余从未满阶且可获得的池中抽取，三张不重复。池不足时明确给出补充修行或有限选项，不出现空白牌、已满阶牌和第三件法宝。

原稿已有“受控随机”方向；以上具体候选约束是新增工程建议。先在单人暂停选择模式验证，多人选择时是否暂停全场留给 G6 决策，不能直接把单人 Time.timeScale=0 搬到联机。[S1，pp.22–23]

### 20.3 本阶段不许回归旧习惯

不能为了证明升级好玩而把四种攻击都升级成无限圆形；不能给唐僧一张随机牌才允许其基础输出成立；不能靠永久成长补偿基本角色缺陷。局外功德、角色解锁、熟练度、商业化与每日玩法仍然延期。

## 21 地图、妖潮、Boss 与多人怎样接回来

### 21.1 G5 先验证一条完整但很短的链

建议先做 5–8 分钟短切片：基础战斗 → 一次路线或地形变化 → 一次守点压力 → 一个 Boss。这个时长是验证工具，不替代原产品约 15 分钟的最终目标。地形先选一种，例如可以改变路线的预设障碍或可利用的地火，不同时制作河流、树林、暴风雪与完整塔防。

妖潮不等于无限加怪：用可控生成节奏制造方向压力，始终遵守活动数量上限。Boss 至少有一种能迫使玩家重新站位、并能被看懂的攻击，不以巨大生命值代替机制。基础攻击仍参与 Boss 战，而不是进入 Boss 后只能等待自动法宝。[S1，pp.8–10、27–35]

### 21.2 主动大招的验证时机

主动大招保留为未来时机决策入口，但 G1–G4 不需要它证明基础战斗成立。G5 在短切片中一次只做一个角色的大招样例，确认主动按钮真的带来“什么时候开”的选择，再扩充其他角色；不要顺带生成技能树和复杂键位。

原稿“移动摇杆 + 一个主动大招”的移动端操作方向保留。大招必须能从统一输入接口触发，单人键盘键位只是开发映射，不直接决定手机布局。[S1，pp.24–25、63]

### 21.3 G6 从双人开始

联网第一轮只验证双人移动、基础攻击、敌人生命与死亡。推荐采用单一权威端裁定伤害和出生，客户端发送输入或明确命令，表现可以局部预测或插值；具体 SDK、传输方式与托管方案在接入前单独形成决策记录。

客户端不得自行提交“我对怪造成了 9999 伤害”作为最终事实。每个技能释放事件与伤害事件具有稳定身份，处理重复包与迟到包；怪物、弹体和粒子不能全部逐帧广播。单人 tick 与事件字段有助于划分责任，但并不自动解决网络预测、延迟与重连。[S1，pp.50–51]

### 21.4 联机必须重新验收的规则

局部视觉命中停顿不能冻结全房间。共享等级、独立构筑继续保留；选择卡牌是否暂停全局、如何处理玩家未选、失联与重连，必须明确。多人生存、元神状态与靠近救援逐项开放，单人 R 键重开不能意外清掉所有队友的局。

先测同机双实例，再测真实跨设备连接；注入 50/100/150 毫秒延迟与少量丢包作为实验条件，记录攻击观感和权威结果，而不是把局域网顺畅当成公网结论。具体目标阈值由真实平台与方案确定，不在前期承诺固定带宽。

### 21.5 保住最终核心

通过网络技术测试以后，还需要真正验证：玩家为何分散、何时支援、为什么愿意回中央，以及集合后四种攻击空间是否形成合作。多人难度优先从方向、特殊威胁、目标数量与机制增加，不通过减半攻速或翻倍法宝冷却削弱玩家。[S1，pp.3、25、38、58–59、65]

单人战斗优秀只证明底座成立；多人“分散 → 合流”的产品身份仍有独立风险，应保持为最终门禁。

## 22 Codex 工作协议：让它持续交付可验证的小步

### 22.1 仓库说明，而不是每次重贴整本报告

在仓库根目录放短小的 AGENTS.md，写当前阶段、禁止事项、代码边界、测试方法和证据要求。完整绿皮书放 docs；当前任务卡引用需要阅读的章节。不要把全部设计文档复制进 AGENTS.md，使关键限制被埋没。

OpenAI 官方文档说明 Codex 会在工作前读取 AGENTS.md，并按全局与项目路径组成指令链；还存在更近路径的覆盖规则和默认文档容量限制。因此启动新会话时应让它报告实际读取的指令来源，不假设文件放在任意子目录都会自动生效。[S4]

### 22.2 一轮标准工作流

先读 AGENTS.md、STATUS.md 和当前任务卡，再检查实际仓库；列出任务理解、受影响文件与拟跑测试；在许可范围内实现一个小的可验收改动；运行相应测试并检查差异；更新任务状态与证据路径；把结果交给人验收，然后停止。

“停止”很重要。当前任务完成后，不因为全文提到了四角色、法宝与联机，就自动开始后续功能。任务卡只能推进到待人工验收，跨门禁必须由负责人更新 STATUS.md。

### 22.3 允许修改范围

任务卡指定文件或目录白名单。确实需要修改其他文件时，先说明理由与风险；依赖升级、工程重建、删除资产、批量改 .meta、数据库/账号/商业化接入、外部发布和付费服务必须单独获准。

Git 作为回退手段，不使用强制推送、覆盖他人分支或删除未提交工作来“解决冲突”。默认不上传源文件、素材或日志到外部服务。许可证、密钥与账号凭据不能放进 AGENTS.md、提示词或仓库。

### 22.4 防止三种最常见的偏航

“写出很多代码但不能打开”：要求场景与输入绑定、构建日志和启动步骤一起交付。“测试失败就删测试”：每个缺陷先保留可复现测试，调整需求必须有决策记录。“为了方便换个引擎或包”：版本与依赖变更必须经过评审，不能把迁移伪装成小修复。

### 22.5 多个 Codex 会话的限制

前期默认串行。确需并行时，仅让一个会话负责运行时代码，另一个负责独立测试或文档；双方使用独立分支与明确文件归属，不同时改同一个场景、同一份配置源或包锁文件。合并顺序与全量回归由一名负责人控制。

## 24 环境检查与测试运行方式

### 24.1 开始前的检查顺序

确认当前目录确实是目标仓库，先查看 git status；读取 ProjectVersion.txt 与 manifest/lock 文件；找到真实 Unity 可执行文件；确认项目没有被另一个编辑器进程独占；检查测试程序集与场景生成入口已存在。没有这些事实，不应直接运行一条想象中的“万能启动命令”。

Codex 本地模式可在有 Unity 与合法运行环境的机器上调用命令。云端或沙箱环境若没有编辑器、许可证或图形环境，只交付能验证的代码与测试文件，并明确让本机补做引擎测试。不得声称它能自动操作一个未接入的 Unity 窗口。

### 24.2 Windows PowerShell 示例

以下是工程具备对应测试后使用的模板；$env:UNITY_EDITOR 必须由开发者设置为真实可执行文件路径。命令依据 Unity Test Framework 的命令行测试入口，具体包版本仍由工程锁定。[S5]

```powershell
$Unity = $env:UNITY_EDITOR
if (-not $Unity -or -not (Test-Path $Unity)) {
    throw "Set UNITY_EDITOR to an existing Unity executable."
}
$Project = (Get-Location).Path
$Out = Join-Path $Project "evidence/local-test"
New-Item -ItemType Directory -Force $Out | Out-Null

& $Unity -batchmode -projectPath $Project -runTests `
    -testPlatform EditMode `
    -testResults (Join-Path $Out "editmode.xml") `
    -logFile (Join-Path $Out "editmode.log")

& $Unity -batchmode -projectPath $Project -runTests `
    -testPlatform PlayMode `
    -testResults (Join-Path $Out "playmode.xml") `
    -logFile (Join-Path $Out "playmode.log")
```

这段示意不添加 -quit，也不使用可能过滤多帧测试的同步运行开关。完整执行脚本还要检查每轮进程结果、日志、XML 是否产生以及执行用例数；缺 XML 或零用例不能当通过。[S5]

### 24.3 稳健执行脚本应做什么

每轮使用唯一输出目录，避免读取旧 XML。依次跑 EditMode 与 PlayMode，第一轮失败则停止。Windows 下确保真正等待 Unity 进程退出；读取退出状态后仍核对测试 XML 中的失败、错误、跳过和总用例数。给出可配置超时，超时仅结束本次创建的进程，不杀掉用户其他编辑器。

编译、测试、生成场景和玩家构建是不同动作。只有测试日志不能证明已经产生可运行 exe/apk；只有构建文件也不能证明通过了测试。构建时记录 BuildReport、目标平台和输出位置，不能在交付说明里混用。

### 24.4 无引擎环境仍能做的事情

可以检查 Markdown/JSON 完整性、参数关系、几何参考测试和文件路径一致性；可以评审 C# 代码，但不能把文本审查称为编译通过。执行包提供的 Python 工具只覆盖规格层，README 和 STATUS 会明确标明边界。

## 25 迭代节奏、分工与变更控制

### 25.1 以交付轮次排，而不是猜日历

第一轮完成环境与可复现入口；第二轮只验证移动；第三轮扇形与静态木桩；第四轮追击、受伤与死亡；第五轮三分钟闭环；第六轮反馈与真人检查。每轮根据任务规模拆分，不要求一次提示词包含一整轮全部功能。

这些是顺序，不是六天承诺。已有工程、引擎经验、测试环境和返工量会改变实际耗时。T00 完成后再由执行者给每张任务卡估算，保留集成与返工时间。

### 25.2 人与 Codex 的责任

负责人决定方向、批准跨阶段、亲自试玩、选择值得解决的问题。Codex 负责按边界实现、提供可重复测试、解释改动与风险。评审者检查代码与证据；同一个人可以兼任负责人和评审者，但不要让“写代码的会话”同时虚构“真人已经认可”。

每次手感讨论必须指向一个可运行版本或同一配置下的录像，而不是讨论不存在的最终画面。

### 25.3 新灵感处理

任何“再加一个……”先写入 backlog，标注解决的问题、依赖阶段和最小验证。只有当前门禁需要它才能继续时，才提范围变更。不能以“这个很简单”作为跳过评审的理由；一个小按钮也可能引入输入、UI、冷却、音效、网络和测试链。

### 25.4 版本冻结

形成可玩的 G1 基线后，冻结一份构建、参数源和配置摘要。之后每次手感实验从该基线分支开始；验证失败就撤回该实验，不把所有试验叠在主线上。引擎和依赖升级单独开任务，不与手感调参混在同一提交。
